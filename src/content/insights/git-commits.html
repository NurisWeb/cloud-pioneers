Seit dem letzten Release melden Monteure, dass ihre Eingaben im Prüfprotokoll verloren gehen. Du öffnest das git log und findest für die fragliche Woche drei Einträge: „Update“, „Fixes“ und „Templates aktualisiert“. Hinter dem letzten stecken 23 geänderte Dateien. Die nächste Stunde liest du Diffs, statt den Fehler zu beheben.

01 Das Problem

Git ist kein Backup

Viele lernen git als Sicherung: Am Ende des Tages git add ., eine Nachricht wie „Update“, git push, und der Code liegt sicher auf dem Server. Das funktioniert, solange niemand zurückschaut. Ein Backup schneidet nach der Uhrzeit. Ein Commit soll nach dem Inhalt schneiden: eine Änderung, ein Grund, eine Nachricht.

Dafür gibt es den Staging-Bereich, die Zwischenablage zwischen Arbeitskopie und Commit. Was du mit git add dort hineinlegst, landet im nächsten Commit, alles andere bleibt liegen. Wer immer alles hineinlegt, verschenkt genau diese Auswahl.

Das Ergebnis siehst du oben am Ende der Sequenz. Mit vier Commits findet git log --grep=Timeout den Fix sofort, und git revert nimmt den Header zurück, ohne die Kontaktseite wiederherzustellen. Mit dem einen Sammel-Commit geht beides nicht.

Das gilt auch, wenn du allein an einem Projekt arbeitest. Dein zukünftiges Ich ist der Kollege, der den Code nicht mehr im Kopf hat. Im Team kommt dazu, dass du überwiegend Commits liest, die du nicht selbst geschrieben hast.

Der häufigste Einwand: „Dann ist das Log voller winziger Commits.“ Ein Commit, der nur eine Hintergrundfarbe ändert, ist trotzdem ein guter Commit. Und wem die vielen kleinen Commits vor dem Merge zu viel sind, fasst sie mit einem Befehl zusammen (Schritt 4 unten). Der umgekehrte Weg, einen großen Commit nachträglich aufzuteilen, heißt: zurücksetzen und jede Zeile neu sortieren.

02 Das Konzept

Eine Nachricht, fünf Teile

Eine Commit-Nachricht hat eine feste Form, und jedes Werkzeug rund um git verlässt sich darauf. git log --oneline, GitHub und GitLab zeigen nur die erste Zeile. Der Rest ist für den, der genauer wissen will, warum. Die Nachricht schreibt sich unten einmal selbst, danach geht die Grafik die fünf Teile durch. Du kannst jeden Teil auch selbst anklicken.

.git/COMMIT_EDITMSG
1fix(session): Timeout auf 60 Sekunden erhöhen
2
3Monteure füllen das Prüfprotokoll am Tablet aus.
4Bei schwachem WLAN dauerte das Speichern länger als
530 Sekunden, die Sitzung lief ab, Eingaben gingen
6verloren.
7
8Refs: WERK-212
Zeile 1: 45 ZeichenBody: höchstens 72 pro Zeile
Aufbau

Fünf Teile, jeder beantwortet eine eigene Frage: Welche Art Änderung? Was bewirkt sie? Warum war sie nötig? Wo steht mehr dazu? Wähle unten einen Teil.

01 Typ und Bereich

fix(session): sagt, welche Art Änderung das ist und wo sie liegt. Das Format kommt aus der Spezifikation Conventional Commits: fix behebt einen Fehler, feat bringt eine neue Funktion, dazu üblich docs, refactor, test, chore. Ein ! nach dem Bereich markiert eine Änderung, die bestehende Nutzung bricht.

02 Betreff

„Timeout auf 60 Sekunden erhöhen“ beschreibt, was der Commit bewirkt, nicht was du getan hast. Also „erhöhen“ statt „erhöht“ oder „habe erhöht“, ohne Punkt am Ende. Die ganze erste Zeile bleibt unter 50 Zeichen. Wird sie länger, steckt meist mehr als eine Änderung im Commit.

03 Leerzeile

Die leere zweite Zeile trennt Betreff und Begründung. git behandelt alles bis zur ersten Leerzeile als Betreff. Fehlt sie, klebt der erste Satz der Begründung in git log --oneline an der Überschrift.

04 Begründung

Der Body erklärt, warum die Änderung nötig war und was vorher schieflief. Das Wie steht im Diff. Das Warum steht nirgends sonst, und genau das fehlt dir in zwei Jahren. Zeilen bricht man nach 72 Zeichen um, damit sie im Terminal lesbar bleiben.

05 Verweis

Die letzte Zeile verknüpft den Commit mit Ticket, Fehlermeldung oder Review. Hier steht auch BREAKING CHANGE: mit einer Erklärung, wenn der Commit bestehende Nutzung bricht.

Nicht jeder Commit braucht alle fünf Teile. Ein korrigierter Tippfehler kommt mit der ersten Zeile aus. Sobald die Frage „Warum?“ nicht offensichtlich ist, gehört die Antwort in den Body.

03 Praxis

So committest du im Alltag

Alle Befehle habe ich in einem frischen Repository mit git 2.43 ausgeführt. Das Skript dazu spielt jeden Schritt automatisch durch.

1. Erst schauen, dann auswählen

Bevor du etwas stagest, verschaff dir einen Überblick. git status zeigt, welche Dateien sich geändert haben, git diff zeigt die Zeilen. Dann legst du gezielt in den Staging-Bereich, was zusammengehört:

Terminal
git status
# nur die zwei Dateien zur Kontaktseite
git add pages/kontakt.html templates/footer.html
# prüfen, was wirklich im Commit landet
git diff --cached --stat

2. Zwei Änderungen in einer Datei trennen

Oft stecken zwei Themen in derselben Datei. git add -p geht die Änderungen Abschnitt für Abschnitt durch und fragt jedes Mal: y nimmt den Abschnitt, n lässt ihn liegen, s teilt ihn in kleinere, e öffnet ihn zum Bearbeiten. Unten drückt der Cursor s, y und n. Danach kannst du die Tasten selbst drücken.

(1/1) Stage this hunk [y,n,q,a,d,s,e,?]?
Arbeitskopie · app.py
@@ -1,6 +1,6 @@
def timeout():
- return 30
+ return 60
bleibt für den nächsten Commit
Teil 2 · Begrüßung
...
- return "Hallo"
+ return "Hallo, Welt"
bleibt für den nächsten Commit

Noch leer.

Eine Datei, zwei Themen: Timeout und Begrüßung.

git add -p · Ausgabe gekürzt

-    return 30

Im Commit landet nur der Timeout. Die Begrüßung bleibt in der Arbeitskopie für den nächsten Commit.

3. Die Nachricht schreiben

Ohne -m öffnet git commit deinen Editor, und du schreibst Betreff, Leerzeile und Body wie oben. Für kurze Nachrichten aus dem Terminal geht es auch mit zweimal -m: Das erste wird der Betreff, das zweite der Body, die Leerzeile setzt git selbst.

Terminal
git commit -m "chore(site): Kontaktseite entfernen" \
  -m "Anfragen laufen seit dem Relaunch über das Formular im Footer."
# Ergebnis prüfen
git log -1 --format=%B

Damit niemand die Form vergisst, legt ihr eine Vorlage ins Repository. git zeigt sie jedes Mal im Editor an, Zeilen mit # landen nicht in der Nachricht:

.gitmessage
# typ(bereich): was der Commit bewirkt, max. 50 Zeichen
# Typen: feat fix docs refactor test build ci chore perf revert
#
# Warum ist die Änderung nötig? Was war vorher das Problem?
#
# Refs: TICKET-123
Terminal · einmal pro Klon
git config commit.template .gitmessage
# zeigt im Editor zusätzlich den Diff unter der Vorlage
git config commit.verbose true

4. Nachbessern, ohne das Log zu verstopfen

Beim Review fällt auf: 60 Sekunden reichen nicht, es müssen 90 sein. Statt eines neuen Commits „Timeout nochmal angepasst“ markierst du die Korrektur als Nachtrag zum ursprünglichen Commit. Vor dem Merge faltet git sie hinein.

Terminal
git log --oneline        # Hash des Ziel-Commits suchen, z. B. 91fd3b7
git add src/session/config.py
git commit --fixup=amend:91fd3b7# Editor öffnet sich: Body und Betreff auf 90 Sekunden ändern,
# die erste Zeile "amend! ..." aber stehen lassen
git rebase -i --autosquash main
# die Liste ist schon sortiert: speichern und schließen

Der Nachtrag geht in seinem Commit auf

4e2b1d9amend! fix(session): Timeout auf 60 Sekunden erhöhen
a71c0e4docs(readme): Tippfehler korrigieren
c03e6a1feat(header): Hintergrund aufhellen
91fd3b7fix(session): Timeout auf 60 Sekunden erhöhen

Vorher: Der Nachtrag steht als eigener Commit oben im Log.

Danach gibt es einen einzigen Commit „fix(session): Timeout auf 90 Sekunden erhöhen“ mit dem richtigen Inhalt. Reicht die alte Nachricht, nimmst du --fixup=91fd3b7 ohne amend:. Genauso fasst du mehrere kleine Commits zusammen: In der Liste von git rebase -i ersetzt du pick durch fixup oder squash.

Nur auf deinem Branch

Rebase schreibt Commits neu. Mach das nur auf deinem eigenen Feature-Branch, bevor er in main landet. Wer Commits neu schreibt, die andere schon geholt haben, bringt deren Klone durcheinander.

5. Das Format im Team absichern

Eine Vereinbarung im Wiki hält zwei Wochen. Ein Hook hält länger: ein Skript, das git vor jedem Commit ausführt. Der commit-msg-Hook bekommt die Nachricht als Datei und kann den Commit mit einem Fehlercode ablehnen. Diese Fassung prüft Typ, Bereich und Länge und lässt von git erzeugte Nachrichten wie Merge, Revert und fixup! durch:

.githooks/commit-msg
#!/bin/sh
# Prüft die erste Zeile der Commit-Nachricht gegen Conventional Commits.
# Ablage: .githooks/commit-msg, aktivieren mit: git config core.hooksPath .githooks
msg_file="$1"
subject=$(grep -v '^#' "$msg_file" | head -n 1)
# Von git erzeugte Nachrichten durchlassen
case "$subject" in
  Merge\ *|Revert\ *|fixup!\ *|squash!\ *|amend!\ *) exit 0 ;;
esac
pattern='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .+'if ! printf '%s\n' "$subject" | grep -Eq "$pattern"; then
  echo "Commit abgelehnt: \"$subject\"" >&2
  echo "Format: typ(bereich): beschreibung, z. B. fix(login): Sitzung nach Timeout beenden" >&2
  exit 1
fi
# Zeichen zählen, nicht Bytes: Umlaute sind in UTF-8 zwei Bytes lang
len=$(printf '%s' "$subject" | LC_ALL=C.UTF-8 wc -m)
if [ "$len" -gt 72 ]; then
  echo "Commit abgelehnt: erste Zeile hat $len Zeichen, erlaubt sind 72." >&2
  echo "Tipp: Passt es nicht in eine Zeile, steckt meist mehr als eine Änderung im Commit." >&2
  exit 1
fi
if [ "$len" -gt 50 ]; then
  echo "Hinweis: erste Zeile hat $len Zeichen, Ziel sind 50." >&2
fi

Über 50 Zeichen gibt der Hook nur einen Hinweis, über 72 lehnt er ab. Der Typ und der Bereich kosten schon 10 bis 15 Zeichen, eine harte Grenze bei 50 würde zu oft greifen. Ins Repository kommt der Hook mit Ausführungsrecht, danach aktiviert ihn jeder einmal in seinem Klon:

Terminal
chmod +x .githooks/commit-msg
git update-index --chmod=+x .githooks/commit-msg   # falls schon ohne Recht eingechecktgit add .githooks && git commit -m "build(git): Hook für Commit-Nachrichten"
# jeder im Team, einmal pro Klon
git config core.hooksPath .githooks

So sah das im Test aus. Drei Versuche, drei Antworten des Hooks:

abgelehnt
$ git commit -m "fix(session): Abmeldung nach Timeout erzwingen ohne Rückfrage"

nur Hinweis
$ git commit -m "feat(api)!: Endpunkt v1 entfernen"

angenommen

Ein lokaler Hook ist eine Hilfe, keine Kontrolle: git commit --no-verify überspringt ihn. Wer das Format verbindlich machen will, prüft die Nachrichten zusätzlich in der CI-Pipeline des Pull Requests. Das habe ich hier nicht aufgesetzt.

6. Die Vereinbarung aufschreiben

Der Hook prüft die Form, nicht den Schnitt. Was ein Commit enthalten soll, gehört als kurze Regel ins Repository, zum Beispiel in die CONTRIBUTING.md:

CONTRIBUTING.md · Ausschnitt
## Commits
- Ein Commit = eine Änderung mit einem Grund. Im Zweifel kleiner.
- Erste Zeile: typ(bereich): was der Commit bewirkt, max. 50 Zeichen.
- Body, wenn das Warum nicht offensichtlich ist. Ticket in die letzte Zeile.
- Nachbesserungen vor dem Merge mit --fixup und rebase --autosquash.
- Einmal pro Klon: git config core.hooksPath .githooks
04 Beim Testen

Was beim Testen passiert ist

Alle Beispiele habe ich mit einem Skript in frischen Repositorys durchgespielt. Diese sechs Dinge sind dabei schiefgegangen.

  • Hook läuft still nicht

    Der Commit „fixed stuff“ ging einfach durch. git meldete nur hint: The '.githooks/commit-msg' hook was ignored because it's not set as executable. Der Hook war ohne Ausführungsrecht kopiert, und git add hatte ihn als 100644 gespeichert. Lösung: chmod +x und, wenn er schon eingecheckt ist, git update-index --chmod=+x.

  • Umlaute verfälschen die Länge

    Der Hook zählte für „… ohne Rückfrage“ 62 Zeichen, es sind 61. wc -m zählt in der Standard-Locale Bytes, und „ü“ ist in UTF-8 zwei Bytes lang. Lösung: LC_ALL=C.UTF-8 wc -m.

  • Fixup mit alter Nachricht

    Nach --fixup und autosquash stand im Code 90, in der Nachricht weiter „60 Sekunden“. Ein einfaches Fixup übernimmt nur den Inhalt. Lösung: --fixup=amend:<hash> (seit git 2.32) und die Nachricht im Editor korrigieren.

  • Amend wird nicht gefaltet

    Nach --fixup=amend: blieb der Nachtrag als eigener Commit stehen. Ich hatte auch die erste Zeile „amend! fix(session): …“ geändert. Über genau diese Zeile findet autosquash sein Ziel. Lösung: nur die Zeilen darunter bearbeiten.

  • Fixup im falschen Commit

    Ich hatte das Ziel per git log --grep="Timeout" gesucht. Getroffen hat das den neueren Commit „Abmeldung nach Timeout …“, der Fix landete dort. Lösung: den Hash aus git log --oneline ablesen und direkt angeben.

  • Suche nach Typ findet zu viel

    git log -E --grep='^fix' fand auch „fixed stuff“. Lösung: --grep='^fix[(!:]' verlangt nach dem Typ eine Klammer, ein Ausrufezeichen oder einen Doppelpunkt.

Zur Version: git rebase --autosquash funktioniert seit git 2.44 auch ohne -i. Mit 2.43 braucht es noch -i. Im Skript habe ich den Editor dafür mit GIT_SEQUENCE_EDITOR=: übersprungen.

Wie groß ist ein Commit?

Faustregel

Lies deine Betreffzeile laut. Wenn du dafür „und“ brauchst, sind es zwei Commits. Wenn du nicht weißt, was du schreiben sollst, weißt du noch nicht, was der Commit tut.

Selbsttest

Du hast heute den Header umgefärbt und einen Timeout-Fehler behoben. Wie committest du?

Zwei Änderungen mit zwei Gründen sind zwei Commits. So kann jemand den Header zurücknehmen, ohne den Fix zu verlieren, und findet den Fix über seine eigene Nachricht.

Warum lieber zu viele kleine Commits als zu wenige große?

Mit fixup oder squash im interaktiven Rebase werden aus fünf Commits einer. Einen großen Commit aufzuteilen heißt dagegen: zurücksetzen und jede Zeile neu sortieren.

Der Hook liegt im Repository, aber bei einer Kollegin läuft er nicht. Was fehlt am wahrscheinlichsten?

core.hooksPath ist eine lokale Einstellung und wird nicht mitgeklont. Und eine Hook-Datei ohne Ausführungsrecht ignoriert git, mit nur einem Hinweis.
