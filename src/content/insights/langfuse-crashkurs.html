Ein Kunde schreibt dem Support-Bot: „Kann ich etwas zurückgeben?“ Der Bot antwortet: „Dazu habe ich nichts gefunden.“ Dabei steht die Rückgabe-Regel in der Wissensbasis. Im Server-Log findest du genau eine Zeile: POST /chat 200. Alles grün, und trotzdem falsch.

  • Mitnehmen 1Ein Trace zerlegt eine Anfrage in verschachtelte Schritte, sodass du siehst, welcher Schritt eine falsche Antwort verursacht hat.
  • Mitnehmen 2Mit @observe und propagate_attributes trägt jeder Schritt in wenigen Zeilen Typ, Nutzer, Session, Modell und Tokens.
  • Mitnehmen 3Ein Experiment mit drei festen Beispielen hat beim Schreiben dieses Beitrags einen echten Retriever-Fehler gefunden, den kein Log gezeigt hätte.

02 Das Problem

Warum Logs bei LLM-Apps nicht reichen

Klassisches Logging ist für deterministische Software gebaut: Gleicher Input, gleicher Output, und wenn etwas schiefgeht, steht ein Stacktrace im Log. Eine LLM-Anwendung verhält sich anders. Dieselbe Frage kann unterschiedliche Antworten erzeugen, ein Agent entscheidet erst zur Laufzeit, welche Werkzeuge er aufruft, und jeder Modellaufruf kostet Geld.

Vor allem schlägt sie leise fehl. Im Szenario oben gab es keinen Fehler und keinen Timeout. Jeder Schritt hat getan, was er sollte, nur das Ergebnis war falsch. Um das zu finden, brauchst du nicht mehr Log-Zeilen, sondern die Kette: Welcher Schritt hat was bekommen und was zurückgegeben?

FrageLog-ZeileTrace
Kam die Anfrage an?jaja
Welche Dokumente hat die Suche geliefert?neinja, als Output des Retrievers
Welcher Prompt ging an das Modell?neinja, als Input der Generation
Wer hat wie viele Tokens verbraucht?neinja, pro Nutzer, Session und Modell
War die Antwort gut?neinmit Scores ja

Langfuse ist eine Open-Source-Plattform für genau diese Kette: Tracing, Prompt-Verwaltung und Evaluation in einem Werkzeug. Der Kern steht unter MIT-Lizenz, du kannst es selbst betreiben oder die Cloud nutzen. Seit Januar 2026 gehört Langfuse zu ClickHouse; Lizenz, Cloud-Adressen und Self-Hosting bleiben laut Ankündigung gleich.

Wofür du Traces brauchst

  • Debugging: Lag es am Retriever oder am Modell?
  • Latenz: Welcher Schritt bremst die Antwort?
  • Kosten: Welcher Nutzer, welches Feature verbraucht die Tokens?
  • Qualität: Ist die neue Prompt-Version besser oder schlechter?

Unter der Haube

Langfuse baut auf OpenTelemetry auf. Eine Observation ist technisch ein OTel-Span mit Zusatzattributen. Deshalb kann jede Sprache mit OTel-Exporter nach Langfuse senden, nicht nur Python und TypeScript.

Instrumentieren

Code wird zum Baum

Links steht der getestete Code, rechts der Trace, den er erzeugt. Der Cursor schaltet einzelne @observe-Zeilen aus und wieder ein, und der Baum ordnet sich neu, so wie es das SDK im Test getan hat. Danach kannst du selbst klicken.

# rag.py · Modell ist eine Attrappe, läuft ohne API-Key
from langfuse import observe, get_client, propagate_attributes

langfuse = get_client()
DOCS = {"Rückgabe": "Rücksendungen sind 30 Tage ...",
        "Versand": "Der Versand dauert 2 bis 4 Werktage."}


def retrieve(question: str) -> list[str]:
    return [t for k, t in DOCS.items()
            if k.lower() in question.lower()]


def generate(question: str, docs: list[str]) -> str:
    answer = docs[0] if docs else "Dazu habe ich nichts gefunden."
    langfuse.update_current_generation(
        model="claude-haiku-4-5",
        usage_details={"input": 412, "output": 18})
    return answer


def rag_answer(question: str) -> str:
    return generate(question, retrieve(question))


def handle(question: str, user_id: str, chat_id: str) -> str:
    
        return rag_answer(question)

Kein Trace: Keine Funktion ist beobachtet.

4 Observations · Root: handle · Nutzer und Session an allen

  • Schalte rag_answer aus: retrieve und answer hängen sich direkt an handle.
  • Schalte handle aus: propagate_attributes wirkt trotzdem, auch ohne Eltern-Observation.
  • Schalte beide aus: retrieve und answer landen in zwei getrennten Traces.

Der Test dazu ruft handle("Wie lange dauert der Versand?", user_id="u-42", chat_id="chat-7") auf und prüft den Baum, der beim Server ankommt. Die Ausgabe war genau die vier Knoten von oben, user.id und session.id standen auch am Retriever.

Ohne Python: OpenTelemetry, zum Beispiel in .NET

Langfuse nimmt Spans von jedem OpenTelemetry-SDK an, über HTTP als JSON oder Protobuf. gRPC geht nicht. Das ist wichtig, weil der .NET-Exporter standardmäßig gRPC spricht. Am einfachsten setzt du die Standard-Variablen, die jedes OTel-SDK liest. Angemeldet wird per Basic Auth mit public_key:secret_key.

Umgebung
AUTH=$(echo -n "pk-lf-...:sk-lf-..." | base64 -w0)
OTEL_EXPORTER_OTLP_ENDPOINT="https://cloud.langfuse.com/api/public/otel"
OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
OTEL_EXPORTER_OTLP_HEADERS="Authorization=Basic $AUTH,x-langfuse-ingestion-version=4"

Das SDK hängt /v1/traces selbst an. Getestet habe ich diese Konfiguration mit dem Python-OTel-SDK gegen den lokalen Ersatz-Server, weil in der Testumgebung kein .NET installiert war.

Was im Hintergrund passiert

Das SDK schickt nicht jeden Span sofort los. Es sammelt fertige Observations in einem Puffer und sendet sie gebündelt im Hintergrund. Das hält deine App schnell, hat aber eine Folge für kurzlebige Prozesse.

Deine App handlerag_answerretrieveanswer Prozess beendet
SDK-Puffer
langfuse.flush() 2 Spans verloren
Langfuse
handlerag_answerretrieveanswer
01

Fertige Funktionen werden Spans. In der Reihenfolge, in der sie enden: erst retrieve, dann answer, dann rag_answer, zuletzt handle.

02

Gebündelt im Hintergrund. Das SDK sendet den Puffer, wenn er voll ist oder ein Intervall abläuft (flush_at, flush_interval). Deine Anfrage wartet nicht darauf.

03

Skript endet, Puffer weg. Ein Skript, ein Notebook oder eine Serverless-Funktion beendet sich, bevor das Intervall abläuft. Was noch im Puffer liegt, kommt nie an.

04

Darum flush() vor dem Ende. langfuse.flush() sendet den Puffer sofort. Danach darf der Prozess enden.

Merksatz

Vor dem Ende von Skripten, Notebooks und Serverless-Funktionen immer langfuse.flush() aufrufen.

In Tests abschalten

In Unit-Tests und in der CI willst du meist keine Traces. Eine Variable reicht, der Code bleibt unverändert. Im Test lief die Pipeline normal durch und beim Server kam kein einziger Span an.

Umgebung
LANGFUSE_TRACING_ENABLED=false
05 Prompts

Ein Label entscheidet, welcher Prompt live ist

Prompts liegen in Langfuse, nicht im Code. Jede Änderung wird eine neue Version, die neueste trägt automatisch latest. Die App fragt nach dem Label production. Der Cursor zieht das Label einmal auf v3 und wieder zurück. Danach kannst du es selbst ziehen oder die Knöpfe nutzen.

langfuse.get_prompt("support-answer") → App bekommt v2

Kein Deploy nötig. Neue Fassungen kommen an, sobald der Cache im SDK abläuft (Standard 60 Sekunden).

⠿ production latest

v1 1. Okt.

Beantworte die Frage freundlich.

erste Fassung, erfindet Fristen

v2 2. Okt.

Beantworte die Frage nur mit diesen Quellen: {{docs}}

Quellenpflicht

v3 4. Okt.

Antworte in einem Satz. Quellen: {{docs}}

kürzer, aber mehr Daumen runter

Weil jede Generation ihre Prompt-Version kennt, siehst du Feedback und Kosten pro Version. Fällt v3 ab, ziehst du das Label zurück auf v2. Das ist die ganze Rücknahme.

prompt.py
prompt = langfuse.get_prompt(
    "support-answer",                 # lädt standardmäßig das Label production
    fallback="Beantworte die Frage nur mit diesen Quellen: {{docs}}",
)
text = prompt.compile(docs="Versand: 2 bis 4 Werktage")
langfuse.update_current_generation(prompt=prompt)  # Version an die Generation hängen

Den fallback habe ich getestet, indem der Server keinen Prompt lieferte: Das SDK meldet den Fehler, gibt den Ersatztext zurück und setzt prompt.is_fallback auf True. So startet deine App auch dann, wenn Langfuse gerade nicht erreichbar ist.

experiment.py
from langfuse import get_client, Evaluation
from rag import rag_answer

langfuse = get_client()
data = [
    {"input": "Wie lange dauert der Versand?", "expected_output": "2 bis 4 Werktage"},
    {"input": "Kann ich etwas zurückgeben?", "expected_output": "30 Tage"},
    {"input": "Habt ihr Gutscheine?", "expected_output": "nichts gefunden"},
]

def task(*, item, **kwargs):
    return rag_answer(item["input"])

def contains_expected(*, input, output, expected_output, **kwargs):
    return Evaluation(name="contains_expected", value=float(expected_output in output))

result = langfuse.run_experiment(
    name="rag-baseline", data=data, task=task, evaluators=[contains_expected]
)
print(result.format())   # zeigt u. a. contains_expected: 0.667

07 Beim Testen

Was beim Testen passiert ist

So wurde getestet

Ohne Langfuse-Konto und ohne Docker: Ein kleiner lokaler Server nimmt die OTLP-Daten des SDK an und gibt den Baum aus (fake_langfuse.py). Die Oberfläche von Langfuse ist deshalb in diesem Beitrag nicht zu sehen, alles andere lief mit dem echten SDK 4.16.0.

  • Masking, das nur Strings kennt, lässt Daten durch

    @observe übergibt den Input als Dictionary: {"args": [...], "kwargs": {...}}. Meine erste Mask-Funktion hat nur Strings ersetzt. Die Ausgabe war sauber, der Input nicht.

    Was beim Server ankommt
    Input{"args": ["anna@example.com"], "kwargs": {}}
    OutputKunde [EMAIL] gefunden

    Input ungefiltert: Die Funktion bekommt ein dict, keinen String.

    observability.py
    import re
from langfuse import Langfuse

EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")

def mask_pii(data, **kwargs):
    # rekursiv, weil @observe Inputs als dict übergibt
    if isinstance(data, str):
        return EMAIL.sub("[EMAIL]", data)
    if isinstance(data, dict):
        return {k: mask_pii(v) for k, v in data.items()}    if isinstance(data, (list, tuple)):
        return [mask_pii(v) for v in data]
    return data

langfuse = Langfuse(
    mask=mask_pii,            # läuft vor dem Export über jeden Input und Output
    sample_rate=0.2,          # nur 20 % der Traces senden
    environment="production",
    release="2026.10.1",
)

  • Sampling ist Zufall, nicht genau 20 Prozent

    Mit sample_rate=0.2 habe ich 500 Aufrufe gemacht. Beim Server kamen 115 an, also 23 Prozent. Das ist richtig so: Jeder Trace wird einzeln ausgelost. Für Kosten pro Nutzer brauchst du deshalb genug Verkehr oder kein Sampling.

    500 Aufrufe, sample_rate=0.2115
    Gemessen im Test: 115 von 500 gesendet.

  • propagate_attributes wirkt nur ab dem Block

    Eine Observation, die vor dem with entsteht, bekommt keine user_id. Im Test hatte der erste lookup vor dem Block keine Nutzer-ID, der zweite im Block schon. Die umgebende Funktion handle bekam sie ebenfalls. Öffne den Block deshalb so früh wie möglich, sonst fehlen Schritte in den Kosten pro Nutzer. Werte für user_id, session_id und Metadaten dürfen höchstens 200 Zeichen lang sein. Nimm IDs, keine E-Mail-Adressen.

  • update_current_trace gibt es nicht mehr

    Ältere Anleitungen setzen Nutzer und Session mit update_current_trace. In SDK 4 ist die Methode entfernt. Ersatz ist propagate_attributes, für Ein- und Ausgabe des Traces set_current_trace_io (bereits als veraltet markiert) und set_current_trace_as_public.

Gewohnheiten, die sich lohnen

  • Sprechende, stabile Namen. retrieve-docs statt func_3. Ändern sich Namen mit jedem Deploy, kannst du Versionen nicht mehr vergleichen.
  • Ab dem ersten Prototyp tracen. Später nachzurüsten ist teurer, und die frühen Fehler sind die lehrreichsten.
  • Mindestens ein Score pro Trace. Ein Daumen vom Nutzer oder eine einfache Prüfung genügt.
  • Jede Woche zehn zufällige Traces lesen. 20 Minuten im Kalender finden Fehler, nach denen niemand gesucht hat.
  • environment und release setzen. Langfuse(environment="production", release="2026.10.05") schreibt beides an jeden Span, so trennst du Test von Produktion und siehst, ab welchem Release etwas anders läuft.
